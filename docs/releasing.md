# 版本发布

发布入口为 `.github/workflows/release.yml`：推送 `vX.Y.Z` 源码标签后触发，标签必须与 `package.json.version` 完全一致，目前只支持稳定的三段版本号。版本、更新说明和源码必须属于同一个发布提交。日常环境与验证命令见[开发与验证](development.md)。以下为后续正常发版流程；保留已有提交历史、版本标签和 Release，不压缩整个仓库为根提交、不移动已发布标签，也不清空历史运行记录。重置已发布版本需要用户另外明确授权。

## 发布步骤

以下以 `1.0.1` 为示例，执行时替换为实际版本和日期。发布需要任务中明确的提交、推送与发布授权；已有授权范围内直接执行，不逐步重复确认。

1. 确认待发布改动已完成审查，检查工作区、分支及远端状态。将 `package.json.version` 和 CHANGELOG 对应章节更新为目标版本；不要使用会自动创建提交和标签的版本命令跳过审查。
2. 从仓库根目录执行以下验证，任一步失败先修复，全部通过后才提交：

   ```bash
   bun run format:check
   bun run check
   bun test
   bun run check:release
   ```

   `check` 包含类型检查和构建；`check:release` 复用该构建准备归档并验证隔离加载，不必再次构建。宿主沙箱由发布工作流验证；本地需要预验时使用[宿主沙箱验证](development.md#宿主沙箱验证)中的固定版本命令。

3. 将版本、CHANGELOG 和相关改动一起提交，合入 `main`。确认没有遗漏或无关改动后推送源码，再在该源码提交上创建标签：

   ```bash
   git push origin main
   git tag -a v1.0.1 -m '发布 TET 1.0.1'
   git push origin refs/tags/v1.0.1
   ```

   创建标签前确认当前 HEAD 就是待发布的 main 提交，且本地与远端都没有该版本标签；发现重名时先查明原因，不强行替换。

4. 查找该源码提交对应的 Test 和 Release 运行，跟进到完成。以下 `<run-id>` 使用实际运行 ID：

   ```bash
   gh run list --limit 10
   gh run watch <run-id> --exit-status
   gh release view v1.0.1
   ```

5. 按下面的完成标准核验远端版本和下载产物，记录结果后交付。

## 完成标准

- Test 与 Release 均成功，源码标签指向预期提交。
- GitHub Release 已公开，包含对应更新说明和 `TET-vX.Y.Z.tar.gz`。
- 下载附件，核对 GitHub 提供的摘要；解包清单的 `gitHead` 与源码提交一致，隔离 Node.js 加载成功。
- 用 Bun 的 `--ignore-scripts` 安装源码仓库或对应标签，确认入口可加载；仅在实际操作过时报告桌面安装通过。

## CHANGELOG 规则

`CHANGELOG.md` 手工维护，是 GitHub Release 正文的唯一来源；不从提交记录自动生成。记录用户或维护者需要知道的行为变化、修复、兼容性及升级操作，不逐条复制 commit。纯重命名、测试整理或拼写修正通常不单列，影响使用或开发要求时再说明。

- 开发时可在顶部 `## 未发布` 汇总待发布变化；发布时整理为新版本章节，最新版本在前，保留旧版本内容。
- 版本标题使用 `## X.Y.Z（YYYY-MM-DD）`，无 `v` 前缀，括号为中文全角，日期为实际发布日期。同一版本只保留一个章节。
- 章节正文不能为空。需要分类时使用三级标题，如 `### 新增`、`### 修复`、`### 变更`、`### 移除`、`### 安全`；只保留有内容的分类。简单版本可直接使用无序列表。
- 破坏性变化在条目前标记 `**破坏性变更：**`，写明受影响的配置或行为以及迁移方式；步骤较长时链接对应说明。
- 版本按语义版本选择：兼容修复递增 patch，兼容功能递增 minor，不兼容变更递增 major。当前版本范围不含预发布后缀。

准备脚本按 `package.json.version` 找到以 `## X.Y.Z（` 开头的首个标题，提取到下一个 `## ` 标题之前的正文，写入 `.release/notes.md`。章节内部不要用二级标题分类。脚本检查版本章节存在且正文非空，但不自动校验日期、排序或重复版本，发版审查时须人工核对。

```markdown
## 未发布

## 1.0.1（2026-11-10）

### 修复

- 修复……，避免……。

## 1.0.0（2026-11-09）
```

## 工作流与失败处理

工作流执行冻结安装、格式检查、`check`、全量测试及固定宿主沙箱。`check` 只构建一次，`release:prepare` 从已有构建创建 `.release/package/` 和 `.release/TET-vX.Y.Z.tar.gz`，并将更新记录对应版本提取到 `.release/notes.md`。归档时间固定，同内容重跑产生相同字节。随后验证源码入口和归档入口，使用 GitHub CLI 创建正式 Release、上传构建包并标为 Latest；不生成产物提交或产物分支。

每版只有一个 `vX.Y.Z` 源码标签，同名 GitHub Release 提供说明和固定版本构建包。工作流在 Release 已存在时验证源码 SHA 并下载附件逐字节比较，不覆盖已有内容；相同版本、源码和产物可安全重跑。若上传中断留下草稿，先排查并删除未完成草稿，再重跑工作流。发布身份需要仓库 `contents: write` 权限。

失败时先运行 `gh run view <run-id> --log-failed` 定位原因。网络或上传等临时故障可对原源码运行 `gh run rerun <run-id> --failed`；若需修改源码，正常做法是修复后发布新版本，不改写已发布标签。不要通过关闭校验、覆盖附件或反复移动标签掩盖不一致。CLI 凭据和 SSH 是不同访问通道；修改工作流时，使用 Token 的通道需要 `workflow` 权限，SSH 使用已有密钥权限。缺少必要访问时报告具体阻塞，不读取或输出 Token。

默认安装地址跟随 `main`，因此主分支只合入可供用户使用的修改；开发中的改动在独立分支审查。Magpie 根据仓库提交变化识别更新，不会自动选择最新 Release 的附件。固定版本使用 `#vX.Y.Z`，安装地址见 [README](../README.md#安装与更新)。
